## 附录：TASK-M10-01 记录（E2E 全 12 旅程 + 覆盖率门禁）

### 运行结果（本机，3 次连续全绿）

```
pnpm test:e2e   → 12 passed（约 27s/次，本地 1 worker）
pnpm test:coverage
  Statements   : 95.85%  (1550/1617)   [阈值 80]
  Branches     : 90.95%  ( 995/1094)   [阈值 70]
  Functions    : 98.67%  ( 594/602)    [阈值 80]
  Lines        : 97.66%  (1340/1372)   [阈值 80]
  （services 99.12 / stores 96.61 行覆盖；services/stores 之外不计入门禁）
```

覆盖率门禁在 `vitest.config.ts` 中只约束 `src/services/**` 与 `src/stores/**`（
docs/testing.md §3 L1 门槛），通过 `pnpm test:coverage` 独立执行；`pnpm verify`
不跑覆盖率（保持 CI 快），e2e.yml 亦不跑单测——职责分离，均记录于此。

### 基础设施决策（M10 记录）

1. **Tauri IPC shim**：浏览器（vite dev + `VITE_TRANSPORT=fetch`）没有 invoke/
   Channel/事件桥，`tests/e2e/tauri-shim.js` 以 `addInitScript` 注入
   `window.__TAURI_INTERNALS__`，实现服务注册表（内存）、健康监控（1.5s 轮询
   /global/health）、SSE（EventSource→Channel）、PTY 通道（客户端回显）与
   `plugin:event|listen`。测试通过 `window.__TAURI_SHIM__` 读遥测。
2. **E03 发消息与流式渲染分离**：mock 的 `prompt_async` 答 204 且不触发 SSE；
   UI 订阅 `/event` 默认重放 happy-chat。旅程 = 乐观气泡 + 204 往返（发），
   + 场景重放渲染 text/tool（流式），中途释放被 hold 的流以控制时序。
3. **场景选择**：UI 不携带 `?scenario=`，旅程用 `page.route` 改写 /event URL
   选择 permission-flow / question-flow / sse-drop；`holdEventStream` 按住首个
   /event 请求直到旅程就绪再放行（timeline 从放行时刻起播）。
4. **`?syncDelay=`（mock 扩展，docs/api-coverage.md §5）**：`server.connected`
   会触发客户端全量 re-sync，其快照替换会清掉 sync 期间到达的 t=0 事件（
   happy-chat 的 `session.created` 与 re-sync 竞争，E2E 首跑暴露）。shim 在
   SSE URL 追加 `syncDelay=250`，让场景在 re-sync 落定后开播。
5. **E12 断网→重连**：`scenario=sse-drop` 播放 3 个事件后断流；EventSource
   自动重连，mock 按连接重放场景 → 再次 `server.connected` → 重置 + re-sync
   （状态自动对齐）。健康腿用 Playwright route 掐断 /global/health → 状态点
   变红 → 恢复 → 变绿；`session.created` 在重连后仍对齐。
6. **tauri-driver 壳级用例（WebdriverIO）**：环境无 tauri-driver（本机未安装
   WebDriver 基础设施，桌面壳级验证归 M10-02/03 的打包首启走查），记为
   文档级条目而非 CI 步骤；e2e.yml 只跑 Playwright 12 旅程。
7. **app bug（E2E 首跑发现并修复）**：`stores/events.ts` 的 `server.connected`
   处理器原会重置 project store 桶，DesktopShell 的按目录订阅 effect 跟踪
   `current`——重置→effect 重建流→新流再发 `server.connected`→再重置，形成
   无限重订阅循环（~70 次/秒）。移除 project 桶重置（syncAll 本就整体重放
   project 列表与 current），1 个连接稳定。L2 测试 mock 了订阅层，未覆盖该
   路径。另记录：re-sync 的整表替换与同步窗口内事件的竞态在真实服务器上
   同样存在（影响面小，事件在后续刷新中自愈）。

## 附录：TASK-M10-02 记录（桌面三平台打包与签名）

### 落地内容

1. **bundle 配置（src-tauri/tauri.conf.json）**：`targets` 由 `"all"` 改为
   显式清单 `["app", "dmg", "nsis", "msi", "deb", "appimage"]`（各平台只构建
   自己子集；Linux 不再产出 rpm——按规格仅 deb + AppImage）；
   `createUpdaterArtifacts: true`——每次构建产出签名 updater 产物（macOS
   `.app.tar.gz` + `.sig`、Windows 安装包旁 `.sig`），供 M8-09 updater 消费
   （latest.json 由 M10-04 发布流水线组装）；`windows.nsis`
   （installMode currentUser）+ `windows.wix`（msi，language en-US）；
   `linux.deb.depends`（libwebkit2gtk-4.1-0 / libayatana-appindicator3-1 /
   librsvg2-2）；macOS 保持 hardenedRuntime 默认（签名/公证走环境变量，见下）。
   注意：Tauri 2 schema 中 MSI 的配置键是 `windows.wix`（target 名仍为
   `msi`），非 `windows.msi`——按真实 schema 落地。
2. **desktop.yml 全量流水线**（M10-02 接管 M0-07 骨架）：矩阵 macos-14
   `--target universal-apple-darwin`（app+dmg，rust targets 含双架构）、
   windows-latest（x86_64，nsis+msi）、ubuntu-22.04（deb+AppImage，完整
   Tauri v2 Linux 依赖：libwebkit2gtk-4.1-dev、build-essential、curl、wget、
   file、libxdo-dev、libssl-dev、libayatana-appindicator3-dev、librsvg2-dev、
   patchelf）；条件签名——macOS 仅在 APPLE_* secrets 存在时导入证书到临时
   keychain 并签名+公证（否则 unsigned）；updater 密钥缺失时用
   `tauri signer generate --ci` 生成一次性 CI 密钥保证未签名验证构建全绿
   （其产物不得发布）；产物按平台上传 artifact。
3. **docs/release-signing.md（新文档）**：三平台签名路线——macOS Developer
   ID 证书 + 公证环境变量（APPLE_CERTIFICATE/APPLE_CERTIFICATE_PASSWORD/
   APPLE_SIGNING_IDENTITY/APPLE_ID/APPLE_PASSWORD/APPLE_TEAM_ID）与
   `spctl`/`stapler` 验证命令；Windows 可选 Authenticode（本地
   certificateThumbprint 或 CI 用 `signCommand` 扩展点，默认 unsigned）；
   Linux 默认 unsigned + 可选 GPG；updater 密钥引用（M8-09 密钥对，绝不入库）。
4. **图标核查**：scaffold 图标集（32x32/128x128/128x128@2x/icon.icns/
   icon.ico/icon.png + Square*/StoreLogo 移动集，Tauri v2 默认图标）已覆盖
   三平台 icns/ico/png 全部尺寸，原样保留（注意：无 icon.svg——桌面端不要求）。
5. **本地验证（macOS arm64，如实记录）**：
   - `pnpm tauri build --ci --bundles app,dmg`（带
     `TAURI_SIGNING_PRIVATE_KEY`）→ `opencoder.app` + `opencoder_0.1.0_aarch64.dmg`
     + updater `.tar.gz` + `.sig`；`.sig` 头部 key-id 与 tauri.conf.json 的
     pubkey 匹配（同一密钥对，`tauri signer sign` 空密码可用——M8-09 生成的
     密钥无密码，文件头 `rsign encrypted` 是 minisign 默认格式）。
   - Info.plist 核对：bundle id `com.opencode.opencoder`、版本 0.1.0、
     LSMinimumSystemVersion 10.13；`codesign -dv` 为 thin arm64、未签名
     （本机无 Apple 证书，符合文档预期）。
   - 首启走查：`open` 启动 bundle 内 app → 主进程存活（13s+ 观察）；退出用
     `pkill`（AppleScript quit 不被处理——与 close-to-tray 设计一致，属应用
     行为非打包问题）；无视觉交互（headless 会话），按任务说明记录步骤。
   - universal 构建 ✓：先 `rustup target add x86_64-apple-darwin`（下载较慢，
     ~4 min），随后 `pnpm tauri build --ci --target universal-apple-darwin
     --bundles app,dmg` 成功——`lipo -info` 确认 fat binary（x86_64 + arm64），
     产出 `opencoder_0.1.0_universal.dmg`（16.4MB）+ updater `.tar.gz` + `.sig`
     （本机耗时约 18 min，含双架构全量编译）。
6. **本地构建前提（环境修复，非仓库改动）**：Homebrew rust 在 PATH 首位且
   缺 `rust-objcopy`（icu_*/zmij 等 build script 需要），导致
   `could not compile ... (build script)`——已 `rustup component add
   llvm-tools-preview` 并将 rustup 工具链
   （`~/.rustup/toolchains/stable-aarch64-apple-darwin/bin`）置于 PATH 前。
   `createUpdaterArtifacts: true` 后未设 `TAURI_SIGNING_PRIVATE_KEY` 的构建
   会在 bundle 阶段快速失败（"A public key has been found, but no private
   key"）——CI 的一次性密钥步骤即为此设计。

### 验收对照

- macOS 本机 ✓（app+dmg+updater 产物、首启进程存活；签名/公证待 Apple 证书，
  文档化）；Windows/Linux 安装包按验收注明为 CI 验证 + 文档化
  （本机无 Windows/Linux 环境）。
